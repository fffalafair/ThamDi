## 1. หลักการทำงาน

1. **ตกลงสัญญา API วันแรก แล้วทำคู่ขนาน** ไม่มีใครต้องรอใคร ยกเว้น 3 จุดเชื่อม (หัวข้อ 4)
2. **คนที่ 1 ทำ mock endpoint ให้คนที่ 2 ภายในวันแรก** หน้าเว็บจะได้ไม่ต้องรอ agent จริง
3. **ทำ eval ให้รันได้ก่อนทำระบบให้ดี** ไม่มีตัวเลข = ไม่มีอะไรนำเสนอ
4. **ทุกงานเสร็จเมื่อผ่าน "นิยามเสร็จ"** (มีเทสต์หรือเดโมได้) ไม่ใช่แค่เขียนโค้ดเสร็จ
5. **จดปัญหาที่เจอทันที** ลงไฟล์ `docs/ISSUES.md` ในรูปแบบ ปัญหา → ต้นเหตุ → แก้อย่างไร
6. **เปลี่ยนสัญญา API ต้องแก้ใน `docs/CONTRACT.md` และบอกอีกคนทันที** ห้ามเปลี่ยนเงียบ ๆ ในโค้ด

## 5. สัญญา API (ร่างสำหรับ `docs/CONTRACT.md`)

| Method | Path | ใครทำ | หน้าที่ |
|---|---|---|---|
| POST | `/api/auth/register` | คนที่ 2 | สมัคร |
| POST | `/api/auth/login` | คนที่ 2 | login → JWT |
| POST | `/api/datasets` | คนที่ 2 | อัปโหลดไฟล์ |
| GET | `/api/datasets` | คนที่ 2 | รายการชุดข้อมูล |
| GET | `/api/datasets/{id}` | คนที่ 2 | schema + แถวตัวอย่าง |
| POST | `/api/chat` | **คนที่ 1** | ถามคำถาม |
| GET | `/api/eval/results` | คนที่ 1 | ผล eval สำหรับหน้าแดชบอร์ด |

### `POST /api/chat`

```json
// request
{ "dataset_id": "ds_123", "question": "ปีงบ 2568 จังหวัดไหนยอดขายสูงสุด" }

// response
{
  "status": "answered",
  "answer": "ในปีงบประมาณ 2568 ...",
  "steps": [
    { "tool": "describe_table", "args": {"name": "orders"}, "status": "ok", "summary": "พบคอลัมน์ ..." },
    { "tool": "run_sql", "status": "error", "sql": "SELECT ...", "detail": "column not found" },
    { "tool": "run_sql", "status": "ok", "sql": "SELECT ...", "rows": 5, "ms": 38 }
  ],
  "table": { "columns": ["จังหวัด", "ยอดขาย"], "rows": [["กรุงเทพมหานคร", 4812350]] },
  "chart": { "type": "bar", "x": "จังหวัด", "y": "ยอดขาย" },
  "meta": { "model": "qwen3-32b", "tokens": 3120, "ms": 2400, "retries": 1 }
}
```

- `status`: `answered` | `clarify` (ถามกลับ) | `refused` (ตอบไม่ได้) | `error`
- `table` และ `chart` เป็น `null` ได้
- **ไฟล์ DuckDB:** `/data/datasets/{dataset_id}.duckdb` เปิดแบบ read-only

## 6. แผนรับมือโควตา LLM

| ข้อจำกัด (free tier ตอนวางแผน) | ผลกระทบ | วิธีรับมือ |
|---|---|---|
| Groq ประมาณ 1,000 ครั้ง/วัน ต่อรุ่น | eval เต็ม ≈ 1,200 ครั้ง | แบ่งรันวันละ 1–2 ระบบ |
| Groq ประมาณ 6,000–12,000 token/นาที | schema ใหญ่ = เรียกได้น้อยครั้งต่อนาที | ส่งเฉพาะตารางที่เกี่ยวข้อง |
| Gemini free tier บางรุ่นจำกัดครั้งต่อวันต่ำมาก | ใช้รัน eval ไม่ได้ | ใช้เป็น fallback เท่านั้น |

**ตารางรัน eval:**

| วันที่ | รันอะไร |
|---|---|
| 29 ต.ค. | ระบบ A (รอบแรก + วัด token) |
| 30 ต.ค. | ระบบ B |
| 31 ต.ค. | ระบบ C |
| 1 พ.ย. | ระบบ D |
| 3 พ.ย. | รอบสุดท้าย (ทุกระบบ หรือเฉพาะที่เปลี่ยน) |

> ถ้าโควตาไม่พอ เติมเงินแบบจ่ายตามใช้ประมาณหลักสิบบาท ตัดสินใจหลังวัด token จริงวันที่ 29 ต.ค.
> ตัวเลขโควตาเปลี่ยนได้ ต้องเช็กหน้า dashboard ของผู้ให้บริการอีกครั้งตอนเริ่ม
