## 1. ภาพรวม

ผู้ใช้อัปโหลดไฟล์ CSV/Excel ของตัวเอง (หรือเลือกชุดข้อมูลตัวอย่าง) แล้วถามเป็นภาษาไทย เช่น

> "ปีงบประมาณ 2568 จังหวัดไหนยอดขายสูงสุด 5 อันดับ"

ระบบตอบเป็นข้อความ พร้อมตารางและกราฟ ผู้ใช้กดดูได้ว่า agent ดูตารางไหน เขียน SQL อะไร ผิดตรงไหน และแก้อย่างไร

### ปัญหาเฉพาะภาษาไทยที่ระบบต้องจัดการ

| ปัญหา | ตัวอย่าง |
|---|---|
| ปี พ.ศ. กับ ค.ศ. | "ปี 2568" ในคำถาม แต่ข้อมูลเก็บเป็น 2025 |
| ปีงบประมาณ | ปีงบ 2568 = ต.ค. 2567 – ก.ย. 2568 |
| ชื่อเดือนและช่วงเวลาแบบไทย | "ไตรมาสแรก", "ช่วงสงกรานต์" |
| ค่าที่สะกดได้หลายแบบ | "กทม", "กรุงเทพฯ", "กรุงเทพมหานคร" |
| ชื่อคอลัมน์ไทยปนอังกฤษ | `ยอดขาย`, `province_name`, `วันที่สั่ง` |

## 3. สถาปัตยกรรม

```
[Next.js]  ─►  [FastAPI: api + agent]  ─►  [Postgres]  ผู้ใช้, ประวัติแชท, metadata ชุดข้อมูล
                     │
                     ├─► [DuckDB]  ไฟล์ข้อมูลของผู้ใช้ (แยกไฟล์ต่อชุดข้อมูล, read-only)
                     └─► [LLM]  Groq ─(ล่ม)─► Gemini ─(ล่ม)─► โหมดคำสั่งพื้นฐาน
```

- ใช้แค่ **3 container**: `web`, `api`, `postgres`
- **DuckDB:** อ่าน CSV/Excel ได้โดยตรง เร็ว ไม่ต้องตั้ง server แยก เปิดแบบ read-only และแยกไฟล์ต่อผู้ใช้

## 4. Agent

### 4.1 Tools

| Tool | หน้าที่ |
|---|---|
| `list_tables()` | ดูว่ามีตารางอะไรบ้าง |
| `describe_table(name)` | คอลัมน์ ชนิดข้อมูล และแถวตัวอย่าง 3 แถว |
| `find_values(column, keyword)` | หาค่าที่ใกล้เคียง เช่น "กทม" → "กรุงเทพมหานคร" |
| `run_sql(query)` | รัน SQL (ต้องผ่านตัวตรวจก่อน) |
| `make_chart(type, x, y)` | ส่งสเปกกราฟให้หน้าเว็บวาด |

### 4.2 รอบการทำงาน

```
คำถาม → ดู schema → (หาค่าถ้าจำเป็น) → เขียน SQL → ตัวตรวจ SQL → รัน
                                              ↑                  │
                                              └───── error ──────┘  (สูงสุด 3 รอบ)
      → ตัวตรวจคำตอบ → ตอบพร้อมตาราง/กราฟ
```

### 4.3 ส่วนที่โค้ดตัดสิน (ไม่ให้ LLM ตัดสิน)

**ตัวตรวจ SQL** (ใช้ sqlglot)
- อนุญาตเฉพาะ `SELECT`
- บล็อก `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ATTACH`, `COPY` และการอ่านไฟล์ภายนอก
- เติม `LIMIT` อัตโนมัติถ้าไม่มี
- ตั้ง timeout ต่อ query

**ตัวตรวจคำตอบ**
- ตัวเลขทุกตัวในคำตอบต้องมีอยู่ในผลลัพธ์ SQL จริง ถ้าไม่มี ให้ตอบใหม่
- ถ้าผลลัพธ์ว่าง ให้ agent ตรวจเงื่อนไขก่อนตอบว่า "ไม่มีข้อมูล" (สาเหตุมักเป็นการสะกดค่าผิดหรือใช้ปีผิด)

**ตัวแปลงวันที่ไทย**
- ฟังก์ชันแปลง พ.ศ. ↔ ค.ศ., ปีงบประมาณ → ช่วงวันที่, ไตรมาส, ชื่อเดือนไทย
- ทดสอบด้วย pytest และ agent เรียกใช้ฟังก์ชันนี้ ไม่ให้ LLM คำนวณเอง

### 4.4 ความปลอดภัย
- **Prompt injection ผ่านข้อมูล:** ส่งเนื้อหาในเซลล์ให้ LLM ในฐานะ "ข้อมูล" ที่แยกชัดจากคำสั่ง และมีกรณีทดสอบในชุดทดสอบ
- **ข้อมูลผู้ใช้:** ส่งแค่ schema กับแถวตัวอย่างให้ LLM ไม่ส่งทั้งไฟล์ และลบไฟล์ที่อัปโหลดอัตโนมัติหลังเวลาที่กำหนด
- **API key:** อยู่ฝั่ง backend เท่านั้น
- **Rate limit:** จำกัดจำนวนข้อความต่อนาทีต่อผู้ใช้

## 6. การวัดผล

### 6.1 ข้อมูลทดสอบ
- **ฐานข้อมูลยอดขายภาษาไทย** สร้างด้วยสคริปต์ (ลูกค้า, สินค้า, คำสั่งซื้อ, สาขา) เพื่อให้รู้คำตอบที่ถูกแน่นอน และใส่กรณียากได้ตามต้องการ
- **ชุดข้อมูลจริง 1 ชุด** จากข้อมูลเปิดภาครัฐ

### 6.2 คำถาม 100 ข้อ 7 หมวด

| หมวด | จำนวน | ตัวอย่าง |
|---|---|---|
| รวม/นับพื้นฐาน | 20 | "มีลูกค้ากี่คน" |
| กรองเงื่อนไข | 15 | "สินค้าราคาเกิน 500 บาท" |
| JOIN หลายตาราง | 15 | "สาขาไหนขายเครื่องดื่มได้มากที่สุด" |
| วันที่และปีแบบไทย | 15 | "ปีงบ 2568", "ไตรมาส 2 ปี 2567" |
| ค่าสะกดหลายแบบ | 15 | "กทม", "เชียงใหม่" (ข้อมูลเขียน "จ.เชียงใหม่") |
| กำกวม → ต้องถามกลับ | 10 | "ยอดขายเป็นยังไงบ้าง" |
| ตอบไม่ได้ → ต้องปฏิเสธ | 10 | ถามถึงคอลัมน์ที่ไม่มีอยู่จริง |

### 6.3 ระบบที่เปรียบเทียบ

| ระบบ | คำอธิบาย |
|---|---|
| A | schema + คำถาม → LLM เขียน SQL ครั้งเดียว |
| B | A + `find_values` |
| C | B + วนแก้ตัวเองเมื่อ error |
| D | C + ตัวแปลงวันที่ไทย + ตัวตรวจคำตอบ (**ระบบเต็ม**) |

### 6.4 ตัวชี้วัด
- **Execution accuracy:** ผลลัพธ์ตรงกับ SQL เฉลยหรือไม่ (เทียบผลลัพธ์ ไม่ใช่ตัว SQL)
- **ความถูกต้องของการถามกลับและการปฏิเสธ**
- **ต้นทุน:** จำนวนรอบที่แก้, token, latency ต่อคำถาม
- **แยกผลรายหมวด** เพื่อดูว่าส่วนไหนของระบบช่วยแก้ปัญหาแบบไหน

### 6.5 ทดสอบระบบ
- **pytest:** ตัวตรวจ SQL (ต้องบล็อกคำสั่งอันตราย 100%), ตัวแปลงวันที่, ตัวตรวจคำตอบ
- **smoke test:** login → อัปโหลด → ถาม → ได้ตาราง
- **CI:** GitHub Actions รัน pytest และ smoke test ทุก PR
- **eval runner:** รันชุด 100 ข้อ บันทึกผลเป็น JSON ให้หน้าแดชบอร์ดอ่าน

## 10. กฎการทำงาน

1. **จดตาราง "ปัญหาที่เจอ → ต้นเหตุ → แก้อย่างไร" ตั้งแต่วันแรก** ไม่ต้องรอเขียนตอนท้าย
2. **ทำ eval ให้รันได้ก่อนระบบจะดี** ไม่มีตัวเลข = ไม่มีอะไรไปนำเสนอ
3. **เก็บผล eval ทุกครั้งที่รัน** ไว้ใช้ทำตารางเปรียบเทียบก่อนและหลังแก้
4. **Git flow:** แตก branch จาก `dev`, เปิด PR, CI ต้องผ่านก่อน merge, ห้าม push ตรงเข้า `main`
5. **ใช้แนวทางวิศวกรรมจากเกณฑ์ได้** (fallback LLM, DEMO_MODE, smoke test, โครง README) แต่ไม่คัดลอกโค้ดโดยตรงถ้าอาจารย์ไม่อนุญาต
6. **อัดคลิปเดโมสำรองเสมอ** เผื่อ API หรืออินเทอร์เน็ตล่ม
